Palestra · What it is and my role

A booking platform each club runs under its own subdomain

A white-label, multi-tenant SaaS for sports clubs, built by a team of four. Next.js and TypeScript on the frontend, a Go API and PostgreSQL.

The product

  • Each club gets its own subdomain, and its data is kept separate from other clubs.
  • Sign-in with email and password or Google. Sessions live on the server, in PostgreSQL; the browser only holds an opaque, HttpOnly cookie.
  • Auth calls go through a small server layer inside the Next.js app (a BFF), so the browser never handles auth tokens.
  • Booking, payment and sign-up from end to end are still in progress.

My role: founder and technical lead

  • Defined the product: a white-label SaaS for each club instead of a marketplace.
  • Set up how the team works: backlog, a GitHub Projects board, issue templates and review rules.
  • Main code reviewer for both repositories, web and API.
  • We work in small, spec-based iterations (Organic-Driven Development). Code is written with AI assistance, and every change is reviewed and verified before it's merged.
Case 01 · Bug report

Safari on iPhone forgets the session

Found while testing sign-in on a real iPhone. The session cookie had no expiry, so Safari could treat it as temporary. The fix spans two repos and had to ship in a specific order.

Verified
Issues and PRs
Issues web#188 and api#239 · PRs web#245 and api#280
Environment
Test environment on our VPS, behind Cloudflare and Nginx (there's no production yet). Real iPhone, Safari on iOS.
Steps
  1. Sign in on a club's subdomain in Safari on iPhone.
  2. Close Safari completely.
  3. Reopen it and go back to the club's site.
Expected
Still signed in. The server keeps the session valid for up to 30 days.
Actual
Sometimes signed out and sent back to the login screen.
Evidence
Set-Cookie: __Host-palestra_session=<token>; Path=/; HttpOnly; Secure; SameSite=Lax
No Expires, no Max-Age.
Root cause
Without an expiry, the browser treats the cookie as a session cookie and may drop it when the browser closes. The session on the server outlives the cookie that points to it.
Fix plan
web#245 (issue web#188): the BFF checks every Set-Cookie it relays from the API. It has to accept the expiry attribute first.
api#280 (issue api#239): the API sends the cookie with an expiry that matches the server session.
Release order
1 · Deploy web#245then2 · Deploy api#280
If the API change went out first, the BFF would reject the new cookie without logging anything, and nobody could sign in. After step 1, I checked Google sign-in in Safari on iOS against the old API before releasing step 2.
Status
Verified on Oct 27, 2026 in the test environment. The session survives closing and reopening the browser in Safari on iOS and in Chrome, Brave, Edge and Firefox on Android. Logout still works in all of them.
__Host-palestra_session Host-only · Path=/ Created: Wed, 28 Oct 2026 01:38:12 GMT Expires: Fri, 27 Nov 2026 01:38:11 GMT HttpOnly · Secure · SameSite=Lax
After the fix, as shown by Firefox's cookie inspector on macOS: the cookie now expires 30 days after sign-in. Verification notes on api#239
Case 02 · First real deploy

Three bugs the mocks couldn't show

Sign-in was tested against a controlled API stub. Once it ran behind Cloudflare and Nginx, three bugs showed up that the stub had no way to reproduce.

01

The origin check failed behind Nginx

Fixed · web#237
Behind the TLS proxy, Next.js 16 built request.url from its internal bind address (https://0.0.0.0:3000), so the BFF's origin check rejected login, session and logout with 403 origin_invalid. Until then, the test environment relied on a workaround that tied each container to a single club. The fix accepts Next's internal host behind the proxy, and the workaround was removed from the server.
02

Google's callback carried extra parameters

Fixed · web#185
The real callback from Google included query parameters the stub never sent. Our parser rejected them, so Google sign-in failed.
03

The session cookie had no expiry

Verified
Safari on iPhone signed users out after closing the browser. Full report in Case 01.

How I diagnosed them

Nginx logs showed what each request looked like by the time it reached the server, which is exactly what the stub had been hiding.

Where the behavior depended on the framework, I read the Next.js source code to see how it handles the request.

Case 03 · Security review

A login CSRF, stopped in code review

In the Google sign-in work, the OAuth state wasn't tied to the browser that started the login. I blocked the PR until it was, so the hole was never merged.

Reference
palestra-api#174, a teammate's PR. My part was the review.
Risk
An attacker could start a Google login with their own account and get someone else's browser to finish it. That person would end up signed in to the attacker's account without noticing.
What changed
The state now lives in a short-lived, host-only cookie in the browser that started the login. The callback is rejected unless it matches.
Set-Cookie: __Host-palestra_google_state=<state>; Path=/; Max-Age=600; HttpOnly; Secure; SameSite=Lax
Status
Fixed before merge. I requested changes, then approved the corrected version and merged it.

Edge

Cloudflare handles DNS and HTTPS for every club subdomain. The server's firewall only accepts traffic coming from Cloudflare.

Server

Nginx terminates TLS and routes to the web and API containers. The BFF relays auth calls to the API. PostgreSQL sits on a private network. Secrets live outside the code.

Email

Transactional email through Resend, with SPF, DKIM and DMARC set up, plus mailbox forwarding for the domain.

Releases

Images are published to GitHub Container Registry. Deploys are manual for now; there's no continuous deployment yet.
Testing

Side project · Sep – Oct 2026

Gestor Académico

A local-first web app for UTN students. It imports SysAcad pages without asking for credentials and shows what you can take next, and when.

What it is

Your data stays in your browser. You import your own SysAcad pages; the app never asks for your login. Hexagonal architecture keeps the academic rules and the page parser separate from the UI.

What it does

  • Prerequisite map for the whole degree
  • Schedule finder with no time clashes
  • Export to a calendar (.ics)
  • Finals and progress tracking

Quality and deploy

Vitest tests for the rules and the parser, CI on GitHub Actions, and deploys to Netlify.
Design decision

Promotions are marked by hand, and the mark survives reimports

Whether a course was passed by promotion is something the student marks. When the SysAcad pages are imported again, that mark is kept instead of overwritten, so a reimport never undoes what the student entered.
